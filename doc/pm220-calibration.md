# Калибровка JXD-PM220: заводская и пользовательская

Статус: предложение на согласование, черновик от 2026-10-07. Firmware этот документ не меняет.
Черновик заводского скрипта: [`scripts/calibration/pm220_factory_cal.py`](../scripts/calibration/pm220_factory_cal.py).

## Коротко

- Сейчас PM220 не калибруется никак. ESPHome `bl0906` считает по номиналам из своего
  `constants.h`, а мы поверх умножаем V, P и E на 0.8, потому что делитель на плате 4×20k,
  а компонент рассчитан на 5×20k. Вдобавок компонент при каждом старте пишет в чип RMSOS от
  чужой платы (Tuya), и малые токи занижаются.
- Предлагаю два слоя. Заводской описывает саму плату измерения без трансформаторов тока.
  Пользовательский — поправку на конкретные CT и монтаж. Действует произведение
  «заводской × пользовательский»; Clear возвращает к заводскому.
- Заводская запись лежит в EEPROM на самой плате JXD-D3-PM1-6 (CAT24C64, 0x56 — проверено по
  схеме) и едет вместе с платой. Формат — `meter.cal` v1, он уже описан и реализован в соседнем
  репозитории `esphome-device-configs` (ветка `feature/meter-cal-record`). Один и тот же файл
  прочитают обе прошивки.
- Пользовательская запись — в FRAM на CPU board, по адресу 0x0200, в двух копиях, с привязкой
  к CRC заводской записи.
- Масштабирование делаем в software, в собственном форке `bl0906`. В register'ы чипа пишем
  только фазовую поправку (PHASE) и пороги creep и восстанавливаем их после каждого сброса чипа.
  Форк нужен в любом случае: убрать захардкоженные RMSOS и получить сырые значения register'ов.
- Энергию считаем по сырым импульсам CF: каждая дельта умножается на коэффициент, который
  действует в этот момент. Смена калибровки больше не даёт скачков счётчиков и не требует
  поднимать версию записи в FRAM.
- Заводская калибровка идёт отдельной factory build с API actions. В серийной прошивке пути
  записи в EEPROM платы измерения нет вообще. Скрипт работает через native API (aioesphomeapi).
- Для пользователя всё выглядит так же, как на PM380: Settings → Calibration → Ref voltage,
  Ref current, Gain (Run, Clear), Offset (Run, Clear), и те же кнопки в HA.

## 1. Что есть сейчас и откуда берутся ошибки

### 1.1 Тракт измерения

По схеме JXD-D3-PM1-6 rev 1.1.0 (лист 4, `Power_meter.SchDoc`):

- **Напряжение.** L → R33…R36, 4×20 kΩ → T1, токовый трансформатор напряжения 1:1 → нагрузка
  R38 100 Ω → фильтр R32/R40 1 kΩ, C33/C35 33 nF → VP/VN. Получается 1.25 mV на вольт сети,
  при 230 V через T1 идёт ≈2.9 mA, на входе чипа ≈287 mV. Для T1 в материалах лежит datasheet
  ZMPT107 (2 mA:2 mA, погрешность −0.6…0 %, фазовый сдвиг ≤45′ при 2 mA и 50 Ω); по BOM тип не
  сверял.
- **Ток.** Внешний CT в разъёмах J4/J6 (MX15EDGVC-3.5-06P, каналы CT1…CT6) → нагрузка 5.1+5.1 Ω
  (R5/R10 для первого канала) → такой же фильтр 1 kΩ / 33 nF → IPn/INn. На схеме есть пометка
  «Коэффициент трансформации для токовых колец 2000:1». Получается 5.1 mV на ампер первичного
  тока. Предел входа ±0.7 V peak при усилении ×1, это ≈97 A первичного тока для синуса.
- **BL0906.** PGA ×1 на всех каналах (GAIN1/GAIN2 по умолчанию), UART 19200 через изолятор
  SCM3725ASA, RST через оптрон LTV-356T от GPIO32 (высокий уровень держит чип в сбросе).
- Фильтры в каналах V и I одинаковые, поэтому их фазовый сдвиг (≈0.6° на 50 Hz) взаимно
  компенсируется и в ошибку не идёт.

### 1.2 Что делает ESPHome `bl0906` (2026.9.1)

- Константы в `constants.h` рассчитаны на 5×20k, 5.1+5.1 Ω и CT 2000:1. Опций калибровки в
  схеме компонента нет.
- `setup()` снимает защиту записи и пишет RMSOS каналов 1…6 так, чтобы вычесть «в квадратах»
  16/15/14/13/12/12 mA — подобрано под референсную плату Tuya. Формула чипа:
  RMS = √(RMS₀² + RMSOS·256) (datasheet, 3.4.4).
- Action `bl0906.reset_energy` делает SOFT_RESET 5A5A5A, а он сбрасывает и register'ы
  калибровки (datasheet, 4.2 и SOFT_RESET 0x9F). RMSOS после этого остаётся нулевым до
  следующей перезагрузки ESP.
- Мы поверх применяем `multiply: 0.8` (substitution `divider_correction` в
  `include/jxd-pm220-e1eth-base.yaml`) к V, P и E. Ток не трогаем — для него константа верная.

### 1.3 Источники ошибок

| Источник | Что искажает | Порядок | Чем закрываем |
| --- | --- | --- | --- |
| Делитель 4×20k против 5×20k в `constants.h` | V, P, E | +25 %, систематически | Сейчас `multiply: 0.8`; в новой схеме — номинальный Kv платы |
| Допуск R33…R36 и R38, погрешность T1 | V, P, E, одинаково по всем каналам | резисторы ±1 % (допуск на схеме не указан), T1 −0.6…0 % | заводской Kv |
| Разброс BL0906 и Vref | все величины | < 1 % по партии (app note); gain error 0.5 %, рассогласование каналов 0.3 % (datasheet 2.4.1) | заводские Kv, Ki, Kp |
| Допуск нагрузки CT 5.1+5.1 Ω | I, P, E канала | ±1 % | заводской Ki |
| Коэффициент самого CT | I, P, E канала | для дешёвых разъёмных CT обычно 1–3 %, зависит от модели | пользовательский gain: CT внешние |
| Чужие RMSOS из `setup()` | малые токи | 50 mA: −5 %, 100 mA: −1.3 %, от 0.5 A: < 0.1 %; ниже 12–16 mA — ноль | убрать в форке, offset считать в software |
| Пороги creep по умолчанию | малые нагрузки | RMS_CREEP 0x200: ток ниже ≈17 mA читается как 0; WA_CREEP 0x04C: мощность ниже ≈0.7 W — 0 и в энергию не идёт | решить осознанно (вопрос 6 из чек-листа, раздел 8) |
| Фазовый сдвиг T1 и CT | P и E при PF < 1 | ошибка 1° даёт 1.3 % при PF 0.8 и 3 % при PF 0.5; при PF 1 — 0.02 % | T1 и плата — заводская PHASE; CT — нет |
| Температура | всё | Vref 20 ppm/°C | не калибруем |

### 1.4 Пример с живого устройства

PM220 на 10.181.24.249, 2026-10-07: 224.75 V; канал 1 — 0.1186 A / 15.21 W; канал 2 —
0.2368 A / 30.45 W; канал 3 — 0.1192 A / 15.34 W; каналы 4–6 — 0. Здесь S = V·I = 26.7 / 53.2 /
26.8 VA, то есть PF ≈ 0.57: нагрузки нелинейные (LED или импульсные блоки питания). Для
калибровки такие не годятся, нужна резистивная. Чужой RMSOS на этих токах съедает ≈1 mA
(0.1197 → 0.1186 A, −0.9 %).

## 2. Модель калибровки

### 2.1 Коэффициенты

Коэффициенты — это чувствительности, LSB на единицу величины, как в `meter.cal`.

| Коэффициент | Что значит | Номинал PM1-6 1.1.0 | Откуда |
| --- | --- | --- | --- |
| Kv | LSB V_RMS на вольт | 14 997.7 | 13162 · 1.25 mV / 1.097 V |
| Ki[n] | LSB I[n]_RMS на ампер первичного тока при 2000:1 | 59 856.4 | 12875 · 5.1 mV / 1.097 V |
| Kp[n] | LSB WATT[n] на ватт | 214.08 | 40.4125 · 5.1 · 1.25 / 1.097² |
| Ioff[n] | шумовой пол тока, A, вычитается в квадратах | 0 | — |
| Poff[n] | мощность без нагрузки, W | 0 | — |
| φ[n] | фазовая ошибка, градусы; «+» значит, что при PF 0.5L плата завышает P | 0 | — |

Энергия одного импульса CF: e[n] = 38.1775 / Kp[n] Wh при CFDIV = 0x10 (app note, раздел про
CF). При номинале это 0.17833 Wh, 5608 импульсов на kWh; 24-bit счётчик канала переполняется
примерно на 2992 kWh. Сверка: номинальные Kv и Kp — это константы ESPHome, умноженные на 1.25,
а Ki совпадает с константой ESPHome как есть.

У идеального чипа Kp = 2.3848·10⁻⁷ · Kv · Ki (40.4125 / (13162 · 12875)). Kp всё равно меряем
отдельно, чтобы поймать отклонение внутренней константы мощности.

Пользовательский слой безразмерный: u_v, u_i[n], u_p[n] (по умолчанию 1). Пользовательские
offset'ы Ioff_u[n] и Poff_u[n], если заданы, заменяют заводские.

### 2.2 Формулы

```text
V     = V_RMS / Kv · u_v
I[n]  = sqrt(max(0, (I_RMS[n] / Ki[n])² − Ioff[n]²)) · u_i[n]
P[n]  = WATT[n] == 0 ? 0 : (WATT[n] / Kp[n] − Poff[n]) · u_p[n]
ΔE[n] = ΔCF[n] · 38.1775 / Kp[n] · u_p[n]          [Wh]
u_p[n] = u_v · u_i[n]                               (пока нет отдельной калибровки P)
P_sum = Σ P[n]
```

- Kv, Ki, Kp, Ioff, Poff и φ берём из заводской записи, а без неё — номинальные.
- WATT = 0 означает, что сработал creep чипа: offset не должен превращать его в нагрузку.
- Poff в энергию не идёт: CF считает чип, а нагрузку без тока отсекает его же creep.
- Сумму считаем сами, а не берём WATT_SUM: register суммы не откалиброван и по умолчанию
  складывает модули (MODE3[8] = 0).
- В форке удобно сразу держать «эффективные» K: Kv_eff = Kv / u_v и так далее (`combine()` в
  приложении A.2). Тогда на каждое значение приходится одно деление.

### 2.3 Слои

- **Заводской** — свой у каждой платы измерения. Пишется один раз на стенде, firmware его
  только читает.
- **Пользовательский** — свой у каждой установки (CT, проводка). Хранится на CPU board в FRAM
  и задаётся относительно заводской записи, к которой привязан через её CRC32. В
  `meter_calibration` для этого прямо предусмотрен `get_record_crc32()`.
- Clear Gain → все u = 1, действует заводской слой. Clear Offset → заводские offset'ы.
- Нет заводской записи (старые платы, статус `missing`) → номинальные значения.
  Пользовательский слой работает и тогда, просто впитывает и погрешность платы.
- Заводская запись сменилась (плату заменили или откалибровали заново) → пользовательский слой
  от старой записи не применяется, и статус об этом говорит. Пользователь делает Clear или новый
  Run.

### 2.4 Software или register'ы чипа

| | Software: raw / K в firmware | Register'ы: CHGN, WATTGN, WATTOS, RMSOS, PHASE |
| --- | --- | --- |
| Форк `bl0906` | нужен всё равно: RMSOS, сырые значения | нужен, плюс запись, read-back и восстановление |
| После сброса чипа | восстанавливать нечего | все register'ы калибровки возвращаются к default'ам; пока firmware их не восстановит, чип врёт на всю поправку (если зашить 0.8 в CHGN[V], то на 25 % по V) |
| Энергия CF | импульсы не откалиброваны: firmware умножает каждую дельту на действующий e[n] | импульсы уже откалиброваны |
| Фаза | для 6 каналов честно не сделать: реактивная мощность есть только у одного канала (MODE3.VAR_I_SEL) | PHASE[n] и PHASE[V], 0.0045° на LSB, всего ±0.57° |
| Диапазон | любой | CHGN ±50 %, PHASE не больше 0.57° |
| Смена коэффициента | мгновенно, без обмена с чипом | unlock, запись, lock, read-back по UART 19200 |
| Совместимость с `meter.cal` | коэффициенты используются как записаны | пересчёт в коды register'ов |
| Пороги creep | работают на неоткалиброванных значениях — разница в проценты, неважно | на откалиброванных |

**Рекомендация — гибрид.** Gain и offset — в software. В чип пишем только PHASE и, если решим
их менять, пороги creep. Что из этого следует:

- энергия считается как ΔCF × e[n] × u_p[n] (раздел 6), а чиповые `Energy_N` и `Total_Energy`
  в HA в нынешнем виде показывать нельзя;
- после сброса чипа восстанавливать приходится только PHASE и creep. Форк каждый цикл читает
  один контрольный register и, если тот вернулся к default'у, переписывает всё (приложение A.1);
- поправка 0.8 как отдельная сущность исчезает: номинальный Kv платы уже учитывает 4×20k.

## 3. Где хранить

### 3.1 Заводская запись — EEPROM на плате измерения

Проверено по схеме JXD-D3-PM1-6 rev 1.1.0, лист 3 (`Connector.SchDoc`): U3 — CAT24C64 (8 KB,
страница 32 байта), подпись «7bits: 0x56h», I2C приходит с сокета CPU (J2, контакты 15/16). WP
подтянут к 3.3 V через R2 10k и посажен на землю через R3 0 Ω, то есть запись разрешена.
Значит, `eeprom_per` действительно на плате измерения, и запись поедет вместе с ней. На
JXD-D3-PM3-3 (PM380) стоит такой же CAT24C64 на 0x56. На CPU board — CAT24C64 на 0x54 и
FM24CL64B на 0x52. В схеме CPU у FRAM по ошибке тоже подписано «0x54h», но scan шины на живом
PM220 видит 0x52, 0x54 и 0x56.

Формат берём готовый: `components/meter_calibration/README.md` в `esphome-device-configs`,
ветка `feature/meter-cal-record` (в `dev` ещё не влита). Образ EEPROM:

| Адрес | Размер | Содержимое |
| --- | --- | --- |
| 0 | 256 | JEEFS board header v4: `JXD-D3-PM1-6`, `1.1.0`, серийник платы (обязателен), CRC32 |
| 256 | 28 | JEEFS file header файла `meter.cal` |
| 284 | 256 | `meter.cal`, запись ниже |
| 540 | — | свободно |
| 8160 | 32 | scratch page для тестов стенда, вне цепочки файлов |

`meter.cal` v1 — 256 байт, little-endian, CRC32 (IEEE) по байтам 0–251. Общая часть: magic
`JHMCAL`, `chip_type` = 2 (BL0906), `channel_count` = 6, модель, ревизия и серийник платы,
калибровочная точка (`ref_voltage_mv`, `ref_current_ua` — вторичный ток), `ct_nominal_ratio` =
2000, `line_freq_hz`, `pga_code` = 0, температура, `flags`, `station_id`,
`ref_instrument_id`, `timestamp`, `operator_code`. Тело BL0906 (байты 128–239):

| Смещение | Поле | Единицы |
| --- | --- | --- |
| 128 | `kv_milli` | u32, Kv × 1000 |
| 132 | `ki_milli[6]` | u32, Ki × 1000, на первичный ампер при 2000:1 |
| 156 | `kp_micro[6]` | u32, Kp × 10⁶ |
| 180 | `phase_mdeg[6]` | i16, φ в тысячных градуса |
| 194 | `i_off_ma[6]` | u16, Ioff в mA первичного тока |
| 206 | `p_off_cw[6]` | i16, Poff в 0.01 W |
| 218 | `err_worst[6]` | i16, худшая ошибка на приёмке, 0.01 % |

`flags`: bit 0 — gain V/I, bit 1 — offset I, bit 2 — offset P, bit 3 — gain энергии (Kp),
bit 4 — фаза, bit 5 — приёмка на стенде пройдена.

Что firmware делает со статусами `meter_calibration` (ни один не останавливает измерение):

| Статус | Что применяем | Что видит пользователь |
| --- | --- | --- |
| `factory` | запись | `Calibration Status`: factory |
| `unverified` | запись | factory, unverified — с warning в логе |
| `missing` | номинал | design values, без warning (старые платы) |
| `corrupt`, `foreign`, `unsupported`, `no_eeprom` | номинал | статус и причина, warning в логе |

Версии: firmware понимает только `record_version` 1. Неизвестную версию считает `unsupported`,
берёт номинал и запись не трогает — новую запись может прочитать только более новая firmware.

### 3.2 Пользовательская запись — FRAM на CPU board

Две копии по 128 байт: A на 0x0200, B на 0x0280. Сохраняем в ту, что старше, поднимая
`sequence`. При загрузке берём валидную копию с большим `sequence`. FRAM пишется за
миллисекунды, но питание может пропасть и в эту миллисекунду, а пользовательская калибровка —
это работа человека, терять её обидно.

```cpp
// PM220 user calibration in FRAM: two slots, the valid one with the higher sequence wins.
// Fields are ordered so the struct has no padding and the CRC covers defined bytes only.
struct UserCalStore {
  float v_gain;                     // 1 = none
  std::array<float, 6> i_gain;      // 1 = none
  std::array<float, 6> p_gain;      // v_gain * i_gain[n] unless measured on its own
  std::array<float, 6> i_offset_a;  // primary A; used where offset_mask has the channel's bit
  std::array<float, 6> p_offset_w;
  uint32_t offset_mask;             // bit n: channel n + 1 has its own no-load offsets
  uint32_t factory_crc32;           // meter.cal this was taken over; 0 = design values
  uint32_t sequence;                // bumped on every save
  uint32_t timestamp;               // UTC of the last change, 0 = unknown
  uint32_t magic;                   // "PMUC"
  uint16_t version;                 // 1
  uint16_t crc;                     // esphome::crc16 up to this field
};
static_assert(sizeof(UserCalStore) == 124, "UserCalStore layout changed, bump USER_CAL_VERSION");
static const uint32_t USER_CAL_MAGIC = 0x504D5543;  // "PMUC"
static const uint16_t USER_CAL_VERSION = 1;
static const uint16_t USER_CAL_ADDRESS[2] = {0x0200, 0x0280};
```

Правила:

- Нет валидной копии — пользовательского слоя нет (все u = 1).
- `factory_crc32` не совпадает с CRC текущей `meter.cal` (или с 0, если записи нет) — слой не
  применяется, в статусе «user calibration belongs to another factory record». Из FRAM ничего не
  стираем, пока пользователь не сделает Run или Clear.
- Неизвестная `version` — копию не трогаем и не используем: её записала более новая firmware.
- Каждый коэффициент при загрузке проверяем на те же пределы, что и при Run (раздел 5.4). Если
  хоть один вне пределов, слой целиком не применяется.
- Factory reset из меню и из HA обнуляет `magic` в обеих копиях: устройство возвращается к
  заводской калибровке. Заводскую запись factory reset не трогает никогда.

### 3.3 Карта FRAM после изменений

| Адрес | Размер | Что | Где описано |
| --- | --- | --- | --- |
| 0x0001 | 1 | тестовый байт стенда | `tests/test-i2c.yaml` |
| 0x0100 | 88 | `EnergyStore` | `include/jxd-pm380-energy-store.h` |
| 0x0180 | 104 | `ChannelEnergyStore`, v3 → v4 (раздел 6) | `include/jxd-pm220-channel-store.h` |
| 0x0200 | 124 (слот 128) | `UserCalStore`, копия A | новое |
| 0x0280 | 124 (слот 128) | `UserCalStore`, копия B | новое |
| 0x0300–0x1FFF | — | свободно | |

В `esphome-device-configs` (ветка `feature/fram-store`) у FRAM другая разметка: 0x0000–0x01FF
отдан стенду, с 0x0200 начинается `fram_store_meter`. При переходе устройства на новую firmware
этот диапазон будет отформатирован, и пользовательская калибровка сама не переедет (вопрос 11
из чек-листа, раздел 8).

### 3.4 Что нужно исправить ещё до того, как завод начнёт писать в EEPROM

1. `tests/test-i2c.yaml` пишет 0xAB, а потом 0x00 по адресу 0x0001 в `eeprom_per` и в
   `eeprom_cpu`. Это второй байт magic `JETHOME`: если тест запустить после записи заголовка,
   плата потеряет и идентичность, и калибровку. Тест нужно перенести на scratch page 0x1FE0
   (8160), как в разметке `esphome-device-configs`.
2. `i2c_eeprom` от pilotak (`github://pilotak/esphome-eeprom`) отправляет `put()` одной
   транзакцией и не режет её по страницам. У CAT24C64 страница 32 байта: запись через границу
   страницы заворачивается в её начало и портит данные. Для FRAM это не страшно, для EEPROM
   платы измерения — страшно. В `esphome-device-configs` лежит vendored-версия того же
   компонента: та же YAML-схема, плюс `page_size`, `type: fram` и защита от записи, которую
   включает `jethome_board_info`. Предлагаю перейти на неё.

## 4. Заводская калибровка

### 4.1 Что именно калибруем

Калибруем плату измерения без CT. CT внешние, вставляются в разъёмы J4/J6 и могут меняться,
поэтому запись описывает плату относительно идеального CT 2000:1 (`ct_nominal_ratio`). Ток на
стенде можно подать двумя способами:

- **(а) Эталонные CT стенда.** Шесть CT 2000:1 класса 0.2S с сертификатом, все на одной
  первичной петле. Источник гонит ток через петлю, и все шесть каналов меряются одновременно.
  Погрешность эталонных CT из сертификата скрипт должен учитывать (TODO в черновике). Этот
  вариант рекомендую: первичные токи от 0.25 до 60 A источник выдаёт легко.
- **(б) Прямая инъекция вторичного тока.** Шесть входов последовательно, ток 2.5 mA
  соответствует 5 A. Нужен источник с точным mA-диапазоном, а на точке 0.25 A это уже 125 µA.

Если CT продаются в комплекте с устройством, соблазнительно калибровать плату вместе с ними.
Не советую: запись окажется привязана к конкретным CT, и после их замены станет неверной.

### 4.2 Оборудование

- Программируемый однофазный источник U/I с регулировкой угла (фиктивная нагрузка) и эталонный
  счётчик или ваттметр класса 0.05–0.1. По сути это поверочная установка для счётчиков.
- Если такой нет: стабильная сеть или источник напряжения, резистивные нагрузки и эталонный
  ваттметр с погрешностью не хуже 0.1 % (уровень Yokogawa WT300). Тогда без фазы и без
  проверки на PF 0.5.
- Жгут из шести эталонных CT (вариант а) или приспособление для инъекции (вариант б).
- Сеть до устройства (Ethernet), ПК с `.venv` этого репозитория.
- 23 ± 5 °C, прогрев 2 минуты под током.

### 4.3 Factory build и защита от случайного запуска

- Отдельная сборка `JXD/jxd-pm220-e1eth-factory.yaml`: серийная конфигурация плюс
  `include/jxd-pm220-factory-cal.yaml` с API actions (приложение A.5). Её прошивают только на
  стенде, после калибровки по OTA ставится серийная firmware, и скрипт проверяет, что
  `Calibration Status` показывает `factory`.
- В серийной firmware нет ни одного пути записи в `eeprom_per`: компонент `jethome_board_info`
  включает защиту `i2c_eeprom` от записи. Это главная защита.
- Factory build не пишет запись, которую не приняла бы серийная firmware (проверяет тем же
  парсером `meter_cal_parse.h`), не пишет заголовок поверх существующего и не трогает ничего
  дальше байта 539.
- API: в factory build ключа нет, и устройство принимает подключение с нулевым PSK (так ESPHome
  ведёт себя, пока HA не выдал ключ). В сети стенда это нормально, наружу такая сборка не
  уходит. В серийной сборке сейчас тоже `encryption:` без ключа, его выдаёт HA при adoption.
- По железу на будущее: вывести WP микросхемы U3 на контакт стенда (сейчас R3 0 Ω намертво сажает
  его на землю), чтобы запись была возможна только на стенде.
- Был вариант с сервисным режимом в серийной firmware, который включается из меню на время. Не
  предлагаю: код записи заводских данных оказался бы на каждом устройстве у клиента.

API actions factory build:

| Action | Аргументы | Ответ |
| --- | --- | --- |
| `cal_info` | — | серийник и модель из заголовка, статус `meter.cal` и причина |
| `cal_raw_mode` | `enabled: bool` | вкл.: номинальные K без offset'ов, PHASE по умолчанию, creep 0, опрос 1 s |
| `cal_set_phase` | `mdeg: int[]` | временно выставить PHASE (для отладки фазы) |
| `cal_measure_start` | `seconds: int` | запустить усреднение |
| `cal_measure_result` | — | `busy` или JSON: `n`, сырые средние V/I/WATT, ΔCF и время, относительное СКО токов, пересчитанные V/I/P |
| `cal_eeprom_read` | `offset: int`, `length: int` | hex, не больше 128 байт за раз |
| `cal_write` | `board_header_hex`, `record_hex` | проверить, записать постранично, прочитать назад, перечитать запись; ответ: статус и CRC32 |

### 4.4 Порядок на стенде

1. Factory build прошит, плата измерения подключена к стенду. Если на EEPROM ещё нет заголовка,
   оператор сканирует серийник, и он передаётся в `--board-serial`.
2. `cal_info`: серийник и текущий статус. При повторной калибровке там будет `factory`.
3. Raw mode.
4. Прогрев: 230 V, 5 A, PF 1, 2 минуты.
5. Ноль: 230 V, ток 0 (CT в цепи), 20 s → шумовой пол I и P по каналам.
6. Gain: 230 V, 5 A, PF 1, 20 s → Kv, Ki[n], Kp[n]. Если коэффициент отличается от номинала
   больше чем на 5 %, плата бракуется: это проводка или неисправная деталь.
7. Фаза, если источник умеет: 230 V, 5 A, PF 0.5L, 20 s → φ[n] из уравнения
   cos(60° − φ) = P_изм / P_эт · cos 60°.
8. Запись `meter.cal` без флага приёмки (статус `unverified`), выход из raw mode. Дальше
   firmware считает ровно так, как будет считать серийная.
9. Приёмка по точкам из таблицы 4.5, по 20 s на точку. На 20 A дополнительно сверяется энергия
   за 60 s.
10. Всё прошло → перезапись с флагом приёмки и `err_worst`, затем read-back образа и проверка
    CRC и статуса. Не прошло → плата идёт в брак или на разбор, запись остаётся `unverified`.
11. Отчёт в JSON: серийник, стенд, эталон, оператор, температура, сырые средние, коэффициенты,
    ошибки по точкам. Его сохраняем в архив.
12. OTA серийной firmware и проверка `Calibration Status`.

По времени выходит 7–8 минут на плату: все шесть каналов меряются одновременно, прогрев можно
совместить с подготовкой следующей платы.

### 4.5 Точки и допуски

Токи даны как первичные при 2000:1. Допуски — для платы с эталоном класса 0.05–0.1.

| Точка | U | I | PF | Проверяем | Допуск |
| --- | --- | --- | --- | --- | --- |
| V 200 | 200 V | 5 A | 1 | V | ±0.3 % |
| V 250 | 250 V | 5 A | 1 | V | ±0.3 % |
| I 0.25 | 230 V | 0.25 A | 1 | I, P | ±1.0 % |
| I 1 | 230 V | 1 A | 1 | I, P | ±0.5 % |
| I 5 | 230 V | 5 A | 1 | V, I, P | ±0.3 / 0.5 / 0.5 % |
| I 20 + энергия | 230 V | 20 A | 1 | I, P; E за 60 s | ±0.5 %; E ±0.5 % плюс 1 импульс |
| PF 0.5L | 230 V | 5 A | 0.5 инд. | I, P | ±0.5 / 1.0 % |
| Без нагрузки | 230 V | 0 | — | I = 0, P = 0 при штатных порогах creep | точно |

Если установка тянет, стоит добавить точку 60 A. Допуски уточним по первым 5–10 платам.

### 4.6 Скрипт

[`scripts/calibration/pm220_factory_cal.py`](../scripts/calibration/pm220_factory_cal.py) —
черновик, это сказано в его docstring.

```sh
# the whole procedure on a simulated board, no hardware needed
.venv/bin/python scripts/calibration/pm220_factory_cal.py --simulate --phase
.venv/bin/python scripts/calibration/pm220_factory_cal.py --simulate --sim-blank   # blank EEPROM
# a real station (needs the factory build, which does not exist yet)
.venv/bin/python scripts/calibration/pm220_factory_cal.py --host 192.168.1.50 \
    --station-id ST1 --instrument-id REF-0001 --operator 7 --ambient 23.5 --phase
```

Что в нём есть: шаги 2–11 из 4.4; расчёт коэффициентов и фазы; сборка `meter.cal`, JEEFS file
header и board header v4 — байт в байт по README `meter_calibration`; проверка записи так же,
как это делает firmware; приёмка по точкам 4.5; отчёт в JSON. Ещё в нём есть модель платы и
эталона для `--simulate`, и эта модель заодно служит эталонной реализацией формул из 2.2.

Совместимость проверена: образ, который собирает скрипт, я прогнал через `jeefs_parse.h` и
`meter_cal_parse.h` с ветки `feature/meter-cal-record` (собрал их на хосте). Заголовок валиден,
`meter.cal` находится по смещению 284, статус — `factory`.

Чего в нём нет: драйверов источника и эталона (сейчас оператор вводит показания вручную, для
автоматизации нужен SCPI под конкретную установку), поправки на сертификат эталонных CT,
сканера серийника и выгрузки отчёта в базу.

Почему native API (aioesphomeapi), а не REST web server:

- API actions принимают типизированные массивы и отвечают JSON'ом. Одно измерение или вся
  запись — это один вызов, и устройство может отказать с понятной причиной.
- Через REST пришлось бы заводить пару десятков number-сущностей, а запись в hex (512 символов)
  не влезает в `text` (максимум 255).
- aioesphomeapi уже стоит в `.venv` как зависимость ESPHome (46.3.0), отдельно ставить нечего.
- Минусы: асинхронный код, и версию aioesphomeapi нужно держать в паре с ESPHome.

### 4.7 А что с PM380

Идея переносится. Сейчас стоковый `atm90e32` хранит пользовательскую калибровку в flash ESP
(preferences, ключ — хеш `_gain_calibration_` и id компонента). При каждом старте он переписывает
register'ы после soft reset, а Clear возвращает значения из YAML (`gain_voltage_N`/`gain_ctN` в
`include/jxd-d3-pm3-3.yaml`, одинаковые номиналы для всех плат). На JXD-D3-PM3-3 есть такой же
CAT24C64 на 0x56, а в `meter.cal` есть тело для ATM90E32 — готовые коды register'ов.

Можно обойтись без форка. Читаем запись до setup'а `atm90e32` и вызываем его публичные сеттеры
(`set_volt_gain`, `set_ct_gain`, `set_*_offset`). Тогда заводские значения становятся теми
«config values», к которым ведёт Clear, а Run работает поверх них: новый gain = ref / measured ×
текущий register. Для этого `atm90e32` нужно опустить по порядку setup (у него `IO`, 900) ниже
`meter_calibration` (598.5) через `setup_priority:`. Проверить на железе. Минус остаётся:
пользовательские gain'ы — абсолютные коды во flash CPU board, к серийнику платы измерения они не
привязаны, так что после замены платы нужен Clear.

## 5. Пользовательская калибровка

### 5.1 Что пользователь может сделать сам

- **Gain по одной точке.** Мультиметр на напряжение и токовые клещи (или розеточный ваттметр,
  который показывает V и I) на одной резистивной нагрузке: чайник, обогреватель, лампа
  накаливания. Напряжение общее; ток — для каждого канала, где есть нагрузка.
- **Ноль без нагрузки** — для каналов, где можно всё выключить.
- **Clear** — возврат к заводской калибровке.
- **Чего не может**: фазу. Для неё нужна нагрузка с известным PF и эталонный ваттметр.

### 5.2 Сущности в HA и web UI

| PM380 (`atm90e32`) | PM220 (предлагаю) |
| --- | --- |
| Phase L1…L3 Ref Voltage | Ref Voltage — одна, напряжение общее |
| Phase L1…L3 Ref Current | Ref Current 1…6 |
| Run / Clear Gain Calibration | так же |
| Run / Clear Offset Calibration | так же, ток и мощность вместе |
| Run / Clear Power Offset Calibration | нет: влито в Offset |
| — | Calibration Status (diagnostic, text) |

Ref-числа — `entity_category: config`, 0 означает «пропустить». После перезагрузки они снова 0,
как и у PM380. Всего 12 сущностей.

### 5.3 Меню

```text
Settings
  Calibration
    Status          Factory+User
    Ref voltage     230.0 V
    Ref current
      Ch1 … Ch6
    Gain
      Run
      Clear  →  "Clear gains?"  →  Yes
    Offset
      Run
      Clear  →  "Clear offsets?"  →  Yes
```

Структура та же, что у PM380. Clear спрятан за подтверждением, как сброс канала: старые gain'ы
после Clear не вернуть. Меню на OLED сейчас правит другая задача, поэтому здесь только
предложение; YAML-набросок — в приложении A.4.

### 5.4 Run Gain

1. Проверить предусловия. Хоть одно Ref-число задано; со времени загрузки прошла минута.
2. Опрашивать чип раз в секунду в течение 20 s, усреднить V, I[n], P[n] и посчитать
   разброс.
3. Для V, если задан Ref Voltage: u_v ← u_v × V_ref / V_изм.
4. Для каждого канала с Ref Current N > 0: u_i[n] ← u_i[n] × I_ref / I_изм и
   u_p[n] ← u_v × u_i[n].
5. Проверить все ограничения. Если хоть одно не прошло, не меняется ничего, и причина уходит в
   статус.
6. Сохранить в FRAM, применить сразу, вывести в лог таблицу «было → стало», как это делает
   `atm90e32`.

Обновление мультипликативное: если всё уже точно, повторный Run почти ничего не меняет.

| Проверка | Порог | Сообщение в статусе |
| --- | --- | --- |
| Напряжение измерено | 150–280 V | no mains voltage |
| Ref Voltage | 150–280 V | reference voltage out of range |
| \|V_ref / V_изм − 1\| | ≤ 10 % | voltage off by X %: check the meter |
| Ref Current | 0.5–100 A | reference current out of range |
| Ток в канале | ≥ 0.4 A | channel N sees X A: wrong channel or CT not on the wire |
| \|I_ref / I_изм − 1\| | ≤ 15 % | channel N off by X %: wrong channel, CT ratio or units |
| PF = \|P\| / (V·I) | ≥ 0.95 | channel N PF 0.62: use a resistive load |
| Стабильность | СКО ≤ 1 % за прогон | the load changed during the run |
| u_v · u_i[n] | 0.8–1.2 | gain out of range |
| Знак P | P > 0 | warning: CT on channel N is reversed (не отказ) |
| Чтение чипа | без ошибок за прогон | meter read errors, try again |

### 5.5 Run Offset

С порогами creep по умолчанию ток ниже ≈17 mA и мощность ниже ≈0.7 W чип и так отдаёт как
ноль, поэтому пользовательский offset заметен только в узкой полосе над порогом. В меню он
нужен для симметрии с PM380 и на случай, если пороги снизим (вопрос 6 из чек-листа, раздел 8). В плане он идёт
вторым приоритетом.

1. На 30 s выключить creep и считать шум каналов при поданном напряжении.
2. Канал принимается, только если I ≤ 30 mA и |P| ≤ 2 W. Иначе он пропускается с сообщением
   «load on channel N (X mA): switch it off or keep its offset».
3. Принятые каналы получают Ioff_u и Poff_u, в `offset_mask` ставится их бит.
4. Вернуть creep, сохранить.

### 5.6 Clear и factory reset

- Clear Gain: u_v = 1, u_i = u_p = 1. Clear Offset: `offset_mask` = 0. В обоих случаях
  сохраняем и применяем сразу.
- Factory reset (Settings → Factory reset, кнопка HA) дополнительно делает недействительными
  обе копии `UserCalStore`. Сейчас обработчик — это `global_preferences->reset()` в
  `include/jxd-pm220-e1eth-display.yaml`. Энергетические счётчики в FRAM factory reset сейчас не
  сбрасывает — это отдельный вопрос (вопрос 8 из чек-листа, раздел 8).

### 5.7 Статус

`Calibration Status` (до 255 символов) — это источник плюс итог последнего действия:

- `factory + user (V, ch1, ch3)`
- `design values: no factory record`
- `factory record corrupt: design values`
- `user calibration not applied: taken over another factory record`
- `gain ok: V +0.42 %, ch1 −1.85 %, ch3 +0.97 %`
- `gain rejected: ch2 PF 0.61, use a resistive load`

В меню строка Status показывает короткую форму (`Factory+User`, `Design`, `Factory`).

## 6. Счётчики энергии и HA

### 6.1 Как сейчас

`include/jxd-pm220-energy.yaml` раз в 10 s берёт состояния `energy_1…6`, а это уже kWh: CF ×
константа ESPHome × 0.8. Разницу с прошлым чтением он добавляет к счётчикам, а сами прошлые
чтения хранит в FRAM в kWh (`ChannelEnergyStore.chip_kwh`). Если поменять масштаб, следующее
чтение расходится с сохранённым, и счётчик прыгает. Поэтому для поправки 0.8 пришлось поднять
`CHANNEL_STORE_VERSION` до 3 и потерять точки отсчёта. С калибровкой масштаб менялся бы
постоянно.

### 6.2 Как предлагаю

- Форк отдаёт сырые CF[n]_CNT, а в FRAM хранятся сырые счётчики.
- Каждые 10 s по каждому каналу считается Δ в импульсах, и к счётчикам добавляется
  Δ × e[n] × u_p[n] с тем коэффициентом, который действует сейчас. Новая калибровка влияет
  только на то, что будет посчитано после неё. Скачков нет, версию поднимать не нужно.
- Наконец-то различаем переполнение 24-bit счётчика и рестарт чипа. Если прошлое значение было
  у самого верха (ближе 1 kWh до 2²⁴), а новое маленькое, — это переполнение:
  Δ = new + 2²⁴ − last. Иначе чип перезапустился, и Δ = new. Защита «больше 1 kWh за проход —
  не считать» остаётся, это 5608 импульсов.
- `ChannelEnergyStore` v4: `std::array<uint32_t, 6> chip_cnt` вместо
  `std::array<float, 6> chip_kwh`. Размер прежний, 104 байта. Значение 0xFFFFFFFF значит
  «неизвестно».
- Переход v3 → v4 без потерь: в v3 лежат kWh, посчитанные как CF × 0.000178330 kWh. Загрузчик
  восстанавливает `chip_cnt = lroundf(chip_kwh / 0.000178330114f)` с точностью до импульса, и
  пользовательские счётчики продолжают идти с того же места.

### 6.3 Что заметит HA

- `Energy_1…6` и `Total_Energy` — это чиповые накопители с `state_class: total_increasing`.
  При калибровке в software их пришлось бы публиковать как «CF × текущий коэффициент», и тогда
  любая смена коэффициента пересчитала бы всю накопленную сумму. HA принимает любое уменьшение
  `total_increasing` за сброс счётчика и прибавляет новое значение целиком — получился бы двойной
  учёт. Значит, эти сенсоры делаем `internal: true`. Для статистики остаются `Energy Channel N`,
  `Energy Today` и остальные счётчики из FRAM: они растут только на дельты.
- Уже сделано: `Energy_1…6` стали `internal: true`, `Total_Energy` удалён. В HA эти сущности
  стали unavailable, их история сохранилась. Дашборды и Energy panel нужно переключить на
  `Energy Channel N`.
- `Total_Power` считаем как Σ P[n], id `total_power` не меняется — его используют страницы
  дисплея.
- После калибровки на графиках V, I и P будет маленькая ступенька. Это честно.
- Прошлое задним числом не исправляется: если пользователь через месяц нашёл ошибку в 3 %,
  посчитанный месяц так и останется.

```cpp
struct RawCycle {
  uint32_t v_rms{0};
  std::array<uint32_t, 6> i_rms{};
  std::array<int32_t, 6> watt{};
  std::array<uint32_t, 6> cf_cnt{};

};

// Turns raw registers into units; pm220_calibration implements it.
class Converter {
 public:
  virtual float volts(uint32_t v_rms) const = 0;
  virtual float amps(int channel, uint32_t i_rms) const = 0;
  virtual float watts(int channel, int32_t watt) const = 0;
};

class BL0906 final : public PollingComponent, public uart::UARTDevice {
 public:
  float get_setup_priority() const override { return setup_priority::DATA - 2.0f; }
  void set_converter(const Converter *converter);  // nullptr: the design values
  // PHASE[1..6] and PHASE[V]; written now and again after every chip reset
  void set_phase_codes(const std::array<uint8_t, 6> &current, uint8_t voltage);
  void set_creep(uint16_t rms_creep, uint16_t wa_creep);  // 0x200 / 0x04C by default
  void add_on_cycle_callback(std::function<void(const RawCycle &)> &&callback);
```

### A.2 Коэффициенты и сложение слоёв

```cpp
// Design values of JXD-D3-PM1-6 rev 1.1.0, see doc/pm220-calibration.md section 2.1
static constexpr float PM16_KV = 13162.0f * 1.25f / 1.097f;                     // LSB per volt
static constexpr float PM16_KI = 12875.0f * 5.1f / 1.097f;                      // LSB per primary A
static constexpr float PM16_KP = 40.4125f * 5.1f * 1.25f / (1.097f * 1.097f);   // LSB per watt
static constexpr double BL0906_CF_WH_X_KP = 4194304.0 * 0.032768 * 16 / (3600.0 * 16);  // CFDIV 0x10

struct FactoryCoefficients {  // from meter.cal, or the design values without one
  float kv{PM16_KV};
  std::array<float, 6> ki{PM16_KI, PM16_KI, PM16_KI, PM16_KI, PM16_KI, PM16_KI};
  std::array<float, 6> kp{PM16_KP, PM16_KP, PM16_KP, PM16_KP, PM16_KP, PM16_KP};
  std::array<float, 6> i_off{};  // A
  std::array<float, 6> p_off{};  // W
  std::array<int16_t, 6> phase_mdeg{};
  uint32_t record_crc32{0};  // 0: design values
};

// The user gains folded into the factory sensitivities: one division per value.
struct Effective final : public esphome::bl0906::Converter {
  float kv;
  std::array<float, 6> ki, kp, i_off, p_off;
  float volts(uint32_t raw) const override { return raw / kv; }
  float amps(int n, uint32_t raw) const override {
    const float a = raw / ki[n];
    const float a2 = a * a - i_off[n] * i_off[n];
    return a2 > 0 ? std::sqrt(a2) : 0.0f;
  }
  float watts(int n, int32_t raw) const override { return raw == 0 ? 0.0f : raw / kp[n] - p_off[n]; }
  double wh_per_pulse(int n) const { return BL0906_CF_WH_X_KP / kp[n]; }
};

inline Effective combine(const FactoryCoefficients &f, const UserCalStore *u) {
  Effective e{};
  e.kv = f.kv / (u ? u->v_gain : 1.0f);
  for (int n = 0; n < 6; n++) {
    const float ui = u ? u->i_gain[n] : 1.0f;
    const float up = u ? u->p_gain[n] : 1.0f;
    const bool own = u != nullptr && (u->offset_mask & (1u << n)) != 0;
    e.ki[n] = f.ki[n] / ui;
    e.kp[n] = f.kp[n] / up;
    e.i_off[n] = (own ? u->i_offset_a[n] : f.i_off[n]) * ui;
    e.p_off[n] = (own ? u->p_offset_w[n] : f.p_off[n]) * up;
  }
  return e;
}
```

### A.6 Проход энергии

```cpp
// The 10 s pass of jxd-pm220-energy.yaml with raw counts
static const uint32_t CHIP_CNT_UNKNOWN = 0xFFFFFFFF;
static const uint32_t MAX_STEP = 5608;  // about 1 kWh at the design Kp
const auto &cycle = id(bl0906_chip).last_cycle();
if (cycle.complete) {
  double delta_wh = 0;
  for (int i = 0; i < 6; i++) {
    const uint32_t cnt = cycle.cf_cnt[i];
    uint32_t &last = id(energy_chip_cnt)[i];
    if (last != CHIP_CNT_UNKNOWN) {
      uint32_t step;
      if (cnt >= last)
        step = cnt - last;
      else if (last > 0xFFFFFFu - MAX_STEP)
        step = cnt + 0x1000000u - last;  // the 24-bit counter wrapped
      else
        step = cnt;  // the chip restarted and counts from zero
      if (step <= MAX_STEP) {
        const double wh = step * id(pm220_cal).wh_per_pulse(i);  // the gain in effect now
        id(energy_channel_wh)[i] += wh;
        delta_wh += wh;
      } else {
        ESP_LOGW("energy", "Channel %d jumped by %u pulses, not counted", i + 1, step);
      }
    }
    last = cnt;
  }
  // slots, today and month get delta_wh as now
}
```
